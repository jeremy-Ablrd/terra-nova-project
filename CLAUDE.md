# Contexte : concours 24h by WebCup 2026

Je suis seul, 24h de développement. Application web pour la ville fictive de Nova Terra (la doc de l'API écrit parfois "Terra Nova" : utiliser "Nova Terra" dans l'interface, comme dans les demandes).
Les demandes viennent d'une API officielle. Un premier lot est disponible dès le lancement, d'autres arrivent par vagues. On est jugé sur des fonctionnalités réellement utilisables et intégrées à l'application.

## Stack
- Laravel 13, PHP 8.4, développement en local, déploiement ensuite sur un serveur HODI
- Interface en français

## API des demandes
- GET https://24h.webcup.fr/wp-json/webcup/v1/requests
- Auth : header X-Webcup-Api-Key. La clé est dans .env (WEBCUP_API_KEY, ou API_KEY en repli, lue via config/services.php), jamais dans le code ni dans ce fichier. Appel côté serveur uniquement.
- Réponse : { api_version, session{...}, requests[...] }. Champs utiles d'une demande : request_code (clé stable), message_public, difficulty_level, xp_total, group_name, sort_order, visible_since_wave (vague d'apparition, 0 = dès le lancement ; remplace wave_number/is_initial).
- Interroger toutes les 30 s (commande artisan planifiée). Stocker en base avec upsert sur request_code. L'interface lit la base, jamais l'API directement.
- arrival_time est un délai depuis le début du concours (02:00:00 = H+2), pas une heure du jour.
- Ne jamais coder en dur le nombre de demandes ni les vagues.

## Règles d'architecture
- Le rôle n'est JAMAIS lu depuis la requête d'inscription : fixé à "citoyen" côté serveur. Les comptes agent et admin viennent d'un seeder.
- Permissions appliquées côté serveur (middleware ou Gates), pas seulement en masquant des liens. Un citoyen sur /agent doit recevoir un 403.
- Séparation stricte : /agent/* réservé au rôle agent, /admin/* au rôle admin. L'admin n'accède ni aux outils agents ni aux demandes des habitants. « Contacter la mairie » (/contact, /contact/confirmation/{demande}, lien de nav, boutons « Nouvelle demande ») est réservé au rôle citoyen (middleware `role:citoyen`) : agent et admin reçoivent un 403.
- Statuts des demandes : enum PHP fixe (nouvelle, en_cours, traitee), avec badge visuel et filtre dans la vue agent.
- Tout changement de statut passe par le service de transition (`App\Services\TransitionDemande::passer()`) : seules transitions nouvelle → en_cours → traitee, verrou `lockForUpdate`, statut affiché revérifié, et dans la même `DB::transaction` : statut, étape `demande_etapes` et entrée du journal. Jamais de `update(['statut' => …])` ailleurs.
- Après l'envoi du formulaire de contact : message de confirmation visible avec un numéro de référence.
- Les demandes des habitants (D04, F22) utilisent le modèle Demande (table demandes, enum Statut, composant statut-badge, DemandePolicy). Ne pas créer de second modèle équivalent. Les demandes de l'API de type exactement « Citoyen » (et elles seules) sont importées dans ce même modèle (user_id null, `request_code` unique, `demandeur_nom`, colonne `type` = `citoyen`, enum `TypeDemande`). Le Centre technique n'affiche et ne compte que les demandes `citoyen` (`Demande::citoyennes()`) : 23 lignes institution/alerte importées par erreur le 03/10/2026 restent en base, masquées (ne jamais les supprimer sans accord) par `ImporteDemandesApi` : jamais d'insert/upsert en masse (save() pour l'événement `created`), jamais d'écrasement d'une demande déjà importée (le statut local prime), et ne jamais supposer qu'une demande a un `user` (utiliser `nom_demandeur`, comparaison stricte sur user_id). Ne pas remettre WithoutModelEvents dans les seeders : la référence est générée par un événement du modèle.
- Journal d'activité (F47, F48) : toute action de modification faite par un agent ou un admin appelle `Journal::enregistrer()` dans la même `DB::transaction` que la modification (sauf la synchronisation manuelle, écrite juste après l'appel : l'API et le verrou de cache interdisent une transaction unique) ; le journal est en lecture seule (aucune route d'écriture, `update()` et `delete()` du modèle `JournalActivite` lèvent une exception) ; jamais de mot de passe, de contenu de message, d'e-mail ni de donnée personnelle dans `detail` ou `objet_libelle` (un compte n'est désigné que par « Compte n° id »). Lecture : agent seul, `/agent/journal`.
- Tableau de bord agent (F50, D19) : `/agent` et `/agent/donnees-api` lisent les données, n'en modifient aucune ; l'actualisation de l'API reste admin (`/admin/synchronisation`). Seule écriture : `users.donnees_api_vues_at` (préférence personnelle, « Marquer comme vues », sans entrée de journal). Les valeurs de synchro viennent du cache `novaterra.session` : jamais de compte à rebours.
- Données personnelles (F55, F56, F33) : toute suppression de compte passe par `App\Services\SuppressionCompte` (compte citoyen seulement : le service refuse un agent ou un admin, donc jamais le dernier admin) ; les demandes sont anonymisées, jamais supprimées (user_id nul, objet et message remplacés, `anonymisee_at` renseigné, référence, service, statuts, dates et étapes conservés) ; compte, sessions, préférences et jetons de réinitialisation sont supprimés, et tout est écrit avec le journal dans une seule `DB::transaction`. Les documents remis à l'habitant (`/mes-donnees/dossier`, `/mes-demandes/recapitulatif` et leurs téléchargements .html) ne contiennent que les données du titulaire (user_id strict) : jamais mot de passe, hash, jeton, session ni nom d'agent ; téléchargements en `Cache-Control: private, no-store`. `estImportee()` se fonde sur `request_code` (user_id nul ne suffit pas).
- Sécurité (F37, F54, F69, F70) : toute route d'agent ou d'admin est protégée par un rôle (`/agent/*` → `role:agent`, `/admin/*` → `role:admin`, test de matrice `MatriceAccesTest`), et toute route avec `{demande}`, `{user}` (compte) ou `{service}` passe par une policy ; chaque 403 sous `/agent` ou `/admin` laisse un événement `acces_refuse` (plafond de 10 par utilisateur et par minute). Le journal de sécurité (`evenements_securite`, conservé 30 jours, `novaterra:purger-securite`) ne contient aucune donnée personnelle : e-mail masqué (`c***@e***.fr`), jamais de mot de passe ni de contenu de message ; écriture par `save()` via `JournalSecurite`. Connexion : `SecuriteConnexion` (e-mail + IP : 5 échecs puis 10 min ; IP seule : 20 en 10 min, désactivable par `NOVATERRA_LIMITE_IP=false` si l'IP est celle d'un proxy ; e-mail seul : 15 en 15 min), message unique. Mots de passe : 10 caractères minimum à l'inscription et au changement seulement (jamais à la connexion), aucun service externe. Pas de double authentification, de lien magique ni d'e-mail.
- En-têtes et CSP (`EnTetesSecurite`) : nosniff, Referrer-Policy, Permissions-Policy, `frame-ancestors 'none'`, HSTS (production et HTTPS seulement, 86400 s, sans includeSubDomains ni preload), CSP sans domaine tiers, mode par `NOVATERRA_CSP_MODE` (`enforce` par défaut, `report-only`, `off` : à rétrograder dans le `.env` si une page casse chez l'hébergeur, puis `php artisan config:clear` si la configuration est en cache). **`'unsafe-eval'` reste dans `script-src`** : Alpine (menus, formulaires) évalue ses expressions avec `new Function` ; les scripts en ligne restent interdits. Remède complet : le build CSP d'Alpine, qui impose de réécrire les expressions des menus (et les assertions de `AccessibiliteTest` qui les citent). Dans les vues : jamais d'attribut `style=""`, ni de gestionnaire `onclick=""` ; utiliser des classes, `x-cloak`, ou un bouton. Une balise `<style>` en ligne n'est permise qu'avec le jeton `Vite::cspNonce()`. Proxys : `TRUSTED_PROXIES` (vide par défaut ; `*` ou une liste d'adresses chez un hébergeur à proxy) ; `/admin/securite` affiche l'adresse IP détectée.
- Exports destinés à l'habitant : tout export est lisible d'abord, informatique ensuite. Livrables principaux : « Mon dossier » (`/mes-donnees/dossier`) et « Récapitulatif de mes demandes » (`/mes-demandes/recapitulatif`), documents en phrases, tableaux accessibles et synthèse, imprimables et téléchargeables en .html autonome (CSS de `resources/css/document.css`, aucun script ni ressource externe). Aucun téléchargement de données brutes (ni JSON, ni CSV) : l'habitant ne reçoit que des documents lisibles et imprimables ; si un format brut revenait un jour, il faudrait y protéger les cellules contre l'injection de formules. Chiffres et phrases calculés une seule fois (`DonneesPersonnelles::dossier()`) ; durées et finalités dans `config/dossier.php`, sens des statuts et phrases dans `lang/fr/dossier.php`, jamais dans une vue.
- Services (F38, F63, F64) : trois états écrits en texte, jamais la couleur seule. Désactivé = coupure d'urgence réservée à l'admin (boutons « Désactiver » / « Réactiver » de `/admin/services`, motif obligatoire, journal dans la même transaction) : le service ne peut plus être choisi dans `/contact` (option désactivée et refus côté serveur). Interrompu = information : le service reste utilisable, la mention prévient. Tout service affiche son état et sa prochaine action possible (`x-disponibilite-service`, `x-prochaine-action`) sur la liste, la fiche et `/urgences`. Textes de la synthèse dans `lang/fr/synthese_services.php` : ne jamais nommer un fichier de langue comme un mot seul utilisé avec `__('Mot')` (sous Windows, `__('Services')` chargerait `services.php`).
- Messages officiels et horaires (F73, F74) : une alerte porte son émetteur officiel (`alertes.emetteur`, liste fermée `App\Enums\Emetteur` : une phrase complète traduite par clé, jamais « de {émetteur} ») ; le bandeau affiche toutes les alertes urgentes en plus de 3 autres au maximum et ne s'appuie sur aucun cache. Un service partenaire est une entrée du catalogue avec un champ `organisme`, pas une entité distincte. Horaires d'ouverture : `services.horaires_semaine` (7 jours, 2 plages au plus par jour, une plage ne passe jamais minuit), état « ouvert / fermé » calculé à chaque requête avec `APP_TIMEZONE` (`Service::etatOuverture()`), jamais mis en cache ; le texte libre `horaires` reste le repli. Le journal ne cite que le nom du champ modifié, jamais une valeur. Textes de langue : fichiers `lang/fr/ouverture_service.php` et `synthese_services.php` (jamais un nom de fichier égal à un mot seul utilisé avec `__()`).
- Chaque nouvelle fonctionnalité doit être reliée à la navigation et à l'existant (pas de page orpheline).
- Code simple et lisible, pas de sur-ingénierie : le temps est limité.
- Après chaque fonctionnalité : lancer les tests ou vérifier la route à la main, puis me résumer en 3 lignes max ce qui a changé.

## Ne pas faire
- Ne pas mettre de secret dans un fichier versionné.
- Ne pas installer de dépendance lourde sans me demander.
- Ne pas démarrer une fonctionnalité sans que je te la demande explicitement.
- Quand un prompt dit d'attendre mon accord, s'arrêter et poser la question.

## Règles transversales
- Langues : tout texte visible (vues, composants, messages de validation et flash) passe par __(), le français étant la langue de base. Aucun texte en dur dans les nouvelles vues. Le sélecteur de langue viendra plus tard.
- Accessibilité : html lang dynamique, un seul h1 par page, landmarks (header, nav, main, footer) avec un lien « Aller au contenu » en premier, chaque champ avec un label associé et ses erreurs liées (aria-describedby), focus visible, aucune information portée par la couleur seule (un badge de statut a toujours un texte), alt sur les images, libellés explicites sur les boutons et liens.
- Thème : couleurs via variables CSS, texte en rem (pas de px fixes pour le texte), pour que « contraste élevé » et « grande taille de texte » soient de simples bascules plus tard.
- Dates : fuseau de l'application `Indian/Reunion` (UTC+4, sans heure d'été) via `APP_TIMEZONE` (config/app.php, .env, .env.example, phpunit.xml). Toute date affichée dans une vue passe par `App\Support\DateLocale::format()` (jj/mm/aaaa HH:mm, heure locale) : aucune date brute ni `translatedFormat` dans les vues. Ne jamais changer APP_TIMEZONE une fois des données écrites (les colonnes datetime sont stockées en heure locale).
- Toute nouvelle page hérite de ces règles. Checklist avant de la livrer :
  1. Elle passe par le layout commun (`x-app-layout` ou `x-guest-layout`) : lien « Aller au contenu » en premier, barre de réglages d'affichage, repères header / nav / main / footer, un seul `<main>` et un seul h1 (dans le slot `header`).
  2. Aucune taille en pixels (ni `text-[14px]`, ni `style="…px"`, ni dans `resources/css/app.css`) et aucune hauteur fixe sur du texte : classes Tailwind (rem), `min-h-*`, `flex-wrap` ; testée en « très grand » et à 200 % de zoom, sans défilement horizontal de la page.
  3. Couleurs : texte ≥ 4,5:1, composants et bordures de champ ≥ 3:1, via les variables CSS de `app.css` ; vérifier aussi le thème « Contraste renforcé » (classe `theme-contraste` sur `<html>`).
  4. Aucune information par la couleur seule : statut, niveau, état actif ou erreur ont toujours un texte, plus une forme (bordure, souligné, gras).
  5. Clavier seul : tout se fait sans souris, focus visible (jamais `outline: none` sans remplacement), pas de piège, Échap ferme menus et fenêtres, cibles ≥ 1,5rem.
  6. Tout texte visible passe par `__()` ; chaque contrôle a un nom accessible (label, `aria-label` ou texte) ; ajouter la page aux tests d'accessibilité (un seul main et un seul h1).
- Sobriété (éco-conception, F57 à F60). Budget par page courante, chargée à froid : 300 Ko transférés au plus et 15 requêtes au plus (`config/eco.php`, mesuré par `node scripts/mesure-poids.mjs` après `npm run build` ; résultats dans `resources/data/mesures-poids.json`, affichés par `/eco-conception`). Toute nouvelle page respecte :
  1. Aucune requête vers un domaine tiers (ni police, ni script, ni image, ni CDN) : polices du système, ressources locales. Aucune URL `http(s)://` externe dans les vues, le CSS et le JS (un test le vérifie ; seul l'espace de noms SVG est toléré).
  2. JavaScript minimal : un seul script (`type="module"`, donc différé), jamais de script bloquant ni en ligne. Aucune fonction essentielle ne dépend du JavaScript (menus et formulaires marchent sans lui ; règles `<noscript>` dans `x-tete-assets`). Pas de nouvelle bibliothèque sans demander.
  3. Images et médias : pas d'image décorative lourde, pas de vidéo ni d'autoplay. Toute `<img>` a `alt`, `width`, `height`, `loading="lazy"` (sauf au-dessus de la ligne de flottaison) et `decoding="async"`, en SVG, WebP ou AVIF. Une information essentielle ne passe jamais par une image seule.
  4. CSS purgé par Tailwind : les classes écrites dans le PHP (`app/**/*.php`) sont couvertes par `tailwind.config.js` ; pas de CSS inutilisé volumineux.
  5. Réseau : cache immuable sur `public/build` et compression dans `public/.htaccess`, chaque directive dans un `<IfModule>` (jamais de 500 si un module manque). Pages connectées en `Cache-Control: private` (`SobrieteReponse`). L'en-tête `Save-Data: on` retire le script (`x-tete-assets`) ; `prefers-reduced-motion` supprime animations et transitions.
  6. Serveur : pas de requête SQL inutile sur les pages publiques (pas de N+1, comptages groupés).
  7. Un nouveau parcours se mesure (`--etape=apres`) et la page `/eco-conception` est mise à jour par le fichier JSON, jamais à la main.
- Navigation : chaque page passe par le layout commun, qui prévoit un emplacement pour un fil d'Ariane.

Reste dépendant de l'hébergeur : compression, en-têtes de cache, `AllowOverride`, stockage de session/cache.
- **Mes données** (F55, F56, F33) : `/mes-donnees` (citoyen seulement, `role:citoyen` ; agent et admin : 403), lien dans la nav citoyen et sur `/espace`. Deux documents lisibles (`/mes-donnees/dossier` et `/mes-demandes/recapitulatif`), à lire, imprimer (feuille d'impression dans `app.css`) ou télécharger en .html autonome ; ni JSON ni CSV. Suppression en deux étapes sans JavaScript : `/mes-donnees/suppression` puis `/suppression/confirmer` (mot de passe + case), limitée à 5 par minute (`suppression-compte`), page publique `/compte-supprime` ensuite. Plus de route `DELETE /profile` ni de modale de suppression. Journal : `CompteSupprime`, acteur « Compte n° X » sans `acteur_id` (seul cas d'acteur citoyen toléré par `Journal::enregistrer`). Les demandes anonymisées restent dans le Centre technique avec « Demandeur supprimé ».
- **Sécurité** : tables `evenements_securite` et `appareils_connus`, services `SecuriteConnexion`, `JournalSecurite`, `AppareilsConnus`, middleware `EnTetesSecurite` et `SobrieteReponse`, `ComptePolicy`. Alerte « nouvelle connexion » (F54) : cookie d'appareil httpOnly de 40 caractères (empreinte SHA-256 en base), encart `role="status"` sur `/espace`, `/agent` et `/admin`, compteur dans la nav, page `/mes-connexions` (tous rôles, son propre compte). Page admin `/admin/securite` (lecture seule) et page publique `/securite` (liée dans le pied de page). Vérification en navigateur réel de la CSP avec Alpine (menus, clavier, déconnexion) : `node scripts/verifier-csp.mjs` après `npm run build`.
- **États des services** (F63, F64) : enum `Disponibilite` (disponible, interrompu, désactivé), colonne `desactive_at`, scope `parPrioriteEtEtat` (prioritaires en tête, puis désactivés et interrompus), `Service::desactiver()` / `reactiver()`. `/services` : synthèse en phrases et filtre par état (`?etat=`), combinable avec `?categorie=`. `/agent` : compteur « services désactivés » en lecture seule.
- **Messages officiels et horaires** (F73, F74) : colonne `alertes.emetteur`, bandeau sans limite pour les urgentes ; colonnes `services.horaires_semaine` (JSON) et `services.organisme`, tableau accessible des horaires et état ouvert/fermé sur la liste et la fiche, saisie par jour (fieldset + legend) dans `/admin/services/{service}/modifier`. Horaires de démonstration : `HorairesServicesSeeder` (idempotent, ne remplit que les services sans horaires structurés ; sur un serveur : `php artisan db:seed --class=HorairesServicesSeeder --force`). Vérification en navigateur réel du bandeau en « Très grand » : `node scripts/verifier-bandeau.mjs` après `npm run build`.
